# VEYQON patches on URY

Branch `veyqon/shared-tenant-safety`, based on ury-erp/ury `version-16@100c43f`. Purpose: install URY on a Frappe 16 / ERPNext site that also runs non-restaurant accounting, stock and manufacturing, without URY changing those records. Every change is a no-op for restaurant records. Each is marked `VEYQON shared-tenant` in the code and is meant to go upstream as a PR.

## Phase 9: payments (S9-25, G-13)

| ID | File | Change |
|---|---|---|
| S9-25 | `ury/ury/api/self_ordering.py` | **Settlement path decided:** a verified provider confirmation marks the submitted Payment Request `Paid` (what ERPNext does for a Phone-channel request, the only kind a POS Invoice gets) and comments on the POS Invoice; the invoice stays draft and the cashier submits it in POS with the online mode of payment (ERPNext `check_phone_payments` refuses a Phone amount that differs from the Paid request). Nothing submits an invoice or creates a Payment Entry. `settle_payment_request` locks the request row, requires amount + currency equal to the request's own (server-made from the invoice), refuses Cancelled/Failed requests and closed invoices (logged as "Self-Order Payment Mismatch" for refund), and is idempotent (repeat = "Already Paid"). `fail_payment_request` never downgrades Paid. |
| S9-25 | `self_ordering.payment_webhook` (new, guest, POST) | Gateway callback: JSON `{payment_request, status: Paid\|Failed, amount, currency, reference}`, header `X-URY-Signature` = hex HMAC-SHA256 of the raw body with site_config `ury_payment_webhook_secret` (constant-time compare; no secret = every call 403). The request's state is the idempotency key, so replays are no-ops. A gateway with its own signature scheme needs a small adapter that verifies it and re-signs. |
| S9-25 | `self_ordering.create_payment_request`, `_ordering_context_response` | Online payment is offered and accepted only when the profile enables it **and** `ury_payment_webhook_secret` is set (`capabilities.online_payment_enabled`). No new Payment Request once one is Paid (no double charge; the rest is paid at the counter). Payment Request creation moved to `_open_payment_request` (shared with G-13). `get_payment_status` reads submitted requests only. |
| G-13 | `ury/ury/api/payment_terminal.py` | New guest POST endpoints `start_terminal_payment(session)`, `get_terminal_payment_status(session)`, `cancel_terminal_payment(session)` (rate-limited per session). Terminal = the non-Offline `URY Payment Terminal` linked to the session's device (QR sessions and devices without one are refused; so is the no-op provider). Amount/currency come from the invoice's Payment Request. One Pending transaction per terminal (row lock; another order gets "busy"; a repeat start returns the pending one). Status moves only Pending → Approved/Declined/Cancelled/Error as the provider reports it to the server; an Approved result whose amount/currency differs is recorded as Error. Approved settles through `settle_payment_request` (same path as S9-25); a settlement failure keeps Approved and logs.
